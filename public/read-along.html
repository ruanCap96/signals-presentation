02 · What is a signal?

A signal holds a value Angular can track.

Create it with signal(); read it by calling it.

  • firstName() reads the current value.
  • set() replaces it with a value you provide.
  • update() derives a replacement from the current value.

The examples start at Morgan; rename toggles to Jaime.

Create, read, and set
const firstName = signal('Morgan');

function rename() {
  const isMorgan = firstName().toLowerCase() === 'morgan';
  firstName.set(isMorgan ? 'Jaime' : 'Morgan');
}

function shout() {
  firstName.update((name) => name.toUpperCase());
}

firstName() → Morgan · after rename() → Jaime · after shout() → JAIME

Why call it? Calling a signal returns its value and tells Angular who read it.

Gotcha. In a template use firstName(), not firstName. The latter refers to the signal, not its value. Signal reads are cheap getters—not work-heavy methods.

03 · Before & after

Signals tell Angular which value changed.

Plain fields still work. Signals make reactive state changes explicit.

Plain field
age = 30;

birthday() {
  this.age = 31;
}

// template
<p>{{ age }}</p>
Signal
age = signal(30);

birthday() {
  this.age.set(31);
}

// template
<p>{{ age() }}</p>

A template that reads age() is a consumer. Updating the signal notifies Angular that the value changed and marks the relevant view for refresh.

Key point. Signals and change detection work together. Angular still refreshes views; signals tell it precisely which state each view depends on.

Note. Angular doesn’t patch individual template expressions, and plain-field code isn’t broken. Signals make reactive state explicit; you don’t have to migrate every field.

04 · Why signals?

Who reads the value that changed?

Angular tracks which signals a reactive consumer reads.

  • A Greeting reads name().
  • A Theme view reads theme().
  • Changing age concerns neither reader.

Shift from “something happened; check everything” to “this value changed; refresh its readers.”

Example consumers
// Greeting consumer
<h1>Hi, {{ name() }}</h1>

// Theme consumer
<body [class]="theme()">

// age changes; neither reads age()
age changes→ no reader here→ unrelated views stay put

In an application. Angular marks the components that read a changed signal for refresh. The interactive demo uses computed() values as stand-ins for those components.

05 · Coming from RxJS? · Optional

For a current UI value, a signal is direct.

BehaviorSubject
name$ = new BehaviorSubject('Ada');

rename() {
  this.name$.next('Bo');
}

// template
{{ name$ | async }}

The async pipe subscribes and renders the latest emission.

Signal
name = signal('Ada');

rename() {
  this.name.set('Bo');
}

// template
{{ name() }}

The value is read directly; no subscription or async pipe is needed for this state.

Key point. This is a simpler way to read a current UI value—not a claim that Observables are obsolete.

RxJS remains useful for streams of events, async composition, timing, cancellation, and other stream-oriented work.

06 · Who uses signals, and where?

Component state can be local or shared.

Signals are useful for synchronous reactive UI state.

Local component state
count = signal(0);

// template
{{ count() }}
Shared service state
@Injectable({ providedIn: 'root' })
export class CounterService {
  count = signal(0);
}

// component
counter = inject(CounterService);

// template
{{ counter.count() }}

Root-provided consumers inject the same service instance and read the same signal.

Real-world example. A notification component can keep a hidden signal and dismiss itself with hidden.set(true).

Gotcha. A shared writable signal can be exposed with asReadonly() to prevent consumers from calling set()/update(). This does not deep-freeze objects inside the signal.

07 · Computed

Derive values with computed().

Signals read inside the callback become dependencies automatically.

  • fullName depends on both name signals.
  • Changing either input invalidates the derived value.
  • A computed signal is read-only; update its inputs instead.
Derived value
const firstName = signal('Maya');
const lastName = signal('Jensen');

const fullName = computed(() =>
  `${firstName()} ${lastName()}`
);

function rename() {
  firstName.set('Theo');
}

// fullName() → Theo Jensen

Good to know. Computed values are lazy and memoized: after a dependency changes, Angular recomputes when the computed is next read. There is no fullName.set().

08 · Test your knowledge

Mutate an object—or replace it?

Signals compare values; mutating an object keeps the same reference.

Start at age 30
user = signal({ name: 'Sam', age: 30 });
age = computed(() => user().age);
Mutation: signal is not notified
user().age += 1;
// age() remains 30
Replacement: new object, notification
user.update(currentUser => ({
  ...currentUser,
  age: currentUser.age + 1
}));
new object→ new reference→ computed updates

update() changes age while preserving Sam’s name.

Mutation. After user().age += 1, the cached computed() still reports 30.

Replacement. Replacing the object with update() after that mutation makes the age jump from 30 to 32. The mutation changed the value silently; only the replacement notified the signal.

Takeaway. For objects and arrays, replace instead of mutating. Arrays: [...items, newItem], not items.push(newItem). Spread is shallow, so copy nested objects too when they change.

09 · Recap

What? Why? How does it simplify state?

What are signals?

Values Angular can track: create with signal(), read with name(), replace with set() or update().

Why were they introduced?

Angular can track which reactive consumers read each signal, so a change concerns its readers.

How does this simplify component state?

Read the value directly; use computed() for derived state, without manually subscribing to that signal.

Manual subscription
name = '';
sub = inject(UserService).name$
  .subscribe((n) => (this.name = n));

ngOnDestroy() {
  this.sub.unsubscribe();
}
Read service signal
name = inject(UserService).name;

// template
{{ name() }}

Cleanup. Reading a signal creates no subscription to clean up. Manual Observable subscriptions may need lifecycle cleanup; the async pipe already manages its own subscription.

ngOnDestroy is still useful for other cleanup, such as timers and event listeners. This example compares manual subscription, not the async pipe.

10 · What comes next?

The signal story continues.

Four APIs connect state, side effects, async data, and RxJS.

effect() · side effects

Runs work in response to signal changes; usually a last resort for propagating state.

effect(() => save(theme()));

linkedSignal() · writable derivation

Derived state that can also be set.

selected = linkedSignal(() => options()[0]);

httpResource() · async data

Models HTTP data, loading, and error state as signals.

user = httpResource(() => `/users/${id()}`);

toSignal() · RxJS interop

Reads an Observable as signal state.

status = toSignal(form.statusChanges);

Try it yourself. The interactive presentation lets you run every example. Check Angular’s current guide before adopting these APIs in production.
